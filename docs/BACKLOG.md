## 一、结论摘要

平台已经完成“任务与机器人的操作系统”底座：

- 项目资料：项目、文档、资源、节点、检查、测试、导出、定时任务、提测、缺陷。
- 任务中心：状态机、LOOP 调度、派单/接受/拒绝、提问、恢复、子任务、交付文档、验收、复盘、停止/取消。
- 机器人：系统/自定义/真人/个人 AGENT、AGENTS.md、技能库、规范库、执行器、模型、负责人、工位。
- 工单工作流：定义/草稿/发布版本、节点/连线、审批/操作/验收、运行推进、交付文档。
- 飞书：OAuth 登录、文档同步、机器人私聊、任务群、卡片、图片/文件、提问卡片。
- 知识库：目录/文章树、全文 + 向量 RRF 检索、Embedding 队列、项目文档镜像。
- MCP：外部 Agent 可列出并调用平台机器人。

尚未完成的上层建筑：

- 研发/测试/发布三条端到端智能体流水线。
- Agent 能力模型与按服务动态装配上下文。
- 统一 Agent 实时状态、运行日志与动画视图。
- LLM 供应商/凭据/配额/成本治理。
- 全局北极星指标与人机任务占比。
- 复盘 → 知识 → 能力更新的自进化闭环。

一句话：

> **下一步不是继续堆功能，而是把“开发流、测试流、项目流”做成可配置、可验收、可度量的智能体流水线；同时补上 Agent 能力模型、统一实时视图、供应商/成本治理和北极星指标。**

## 二、目标与主线

### 2.1 核心命题

从“以组织为中心”转向“以 AI 为中心”：

| 维度 | 以组织为中心 | 以 AI 为中心 |
|---|---|---|
| 上限 | 受人的阅读量、精力、流程损耗限制 | 受算力、上下文与治理能力限制 |
| 敏捷度 | 组织越大越臃肿、越慢 | 机器人可复制、可弹性扩张 |
| 人的精力 | 大量投入过程协调 | 更多投入目标、设计、异常、验收 |
| 响应周期 | 天级 | 秒级、分钟级 |
| 弹性 | 业务扩张需要加人 | 业务扩张主要加机器人与 token |
| 计价 | 人天 | token、时长、结果 |

人的价值转变：

- 从“直接执行任务”转为“设计机器人、培训机器人、设定目标、处理异常、验收结果”。
- 人是机器人的生产者、拥有者、维护者、责任者。
- 业务绩效由人牵头；职能绩效由“生产机器人 + 机器人完成任务”构成。

### 2.2 四层结构

```text
                    ┌──────────────────────────────┐
                    │  以 AI 为中心，而不是以组织为中心  │
                    └──────────────┬───────────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        │                          │                          │
   ① 协作层                   ② 流程层                   ③ 运行层
   人（责任者）               开发流 / 测试流              LOOP 调度
      ↓                       项目流 / 发布流              任务状态机
   代理机器人                   审批 / 验收                 执行器 OpenCode
      ↓                          ↓                          ↓
   专家机器人网络             交付物 / 工单 / 文档          实时流 / 日志
        │                          │                          │
        └──────────────────────────┼──────────────────────────┘
                                   │
                             ④ 数据层
                    全链路留存 / 知识库 / 指标 / RSI
```

### 2.3 四个闭环

1. **任务闭环**：需求 → 派单 → 接受 → 执行 → 提问/反馈 → 交付 → 验收 → 复盘。
2. **研发闭环**：需求 → 架构方案 → 人工确认 → 开发任务 → 代码/文档交付 → 测试 → 发布。
3. **交付闭环**：项目交付物 → 提测 → 缺陷 → 修复 → 发布 → 验收。
4. **学习闭环**：任务/对话/文档/复盘 → 知识库 → 机器人能力更新 → 下一次任务。

## 六、当前最该补的六个缺口

### 6.1 Agent 能力模型 + 上下文包（B7/B8）

问题：按前端/后端硬编码角色会组合爆炸；靠 AGENTS.md 手写上下文不可复用。

建议：

- Worker 增加 `capabilities`（如 `frontend`、`backend`、`data`、`qa`、`release`）。
- 增加 `serviceScopes` / `repos` / `techStack` / `knowledgeScopes`。
- 任务定义声明“需要什么能力”。
- 派单时按能力匹配机器人，并自动装配 context pack：
  - 服务/仓库信息
  - 技术栈与规范
  - 相关文档/知识
  - 历史任务与复盘
  - 技能与工具
- 角色粒度从粗到细：先 `研发/测试/发布`，再按服务/仓库细分。

验收标准：同一个机器人可接多类任务；新增服务只需新增 context pack，不新增角色。

### 6.2 通用工作流引擎 + 节点契约（C3/C4/C9）

当前工单工作流是很好的起点，但只服务工单。

建议：

- 工作流定义增加 `kind`（ticket / pipeline / release）。
- 节点增加输入/输出契约：
  - `inputSchema`：字段、文档、产物、上下文引用。
  - `outputSchema`：必须产出的文档/文件/结论。
  - `acceptanceRules`：自动校验或人工验收。
- 运行时增加可视化：当前节点、执行中/等待中、耗时、产物、日志。
- 保留现有工单运行时，增量扩展，不重写。

验收标准：同一套引擎可定义开发流、测试流、项目流、审批流，且运行时可追踪。

### 6.3 三条流水线 MVP（C5/C6/C7）

先做最小闭环，不追求全自动。

**开发流**

```text
需求 → 架构师 Agent（技术方案）→ 人工确认 → 开发任务（仓库/分支）
→ 代码/文档交付 → 测试任务 → 人工验收
```

**测试流**

```text
需求 + 技术方案 → 质量 Agent（测试方案）→ 人工确认
→ 测试用例/脚本 → 执行 → 缺陷 → 回归
```

**项目流**

```text
测试用例 + 技术交付物 → 发布 Agent → 发布工单（审批）→ 发布 → 验收
```

验收标准：至少一条端到端流程可在平台上发起、暂停等待人工确认、继续执行并验收。

### 6.4 统一实时视图（B11/B12/D6）

建议新增 `/agents` 或升级 `/tasks/live`：

- 全部 Agent 实时状态：空闲 / 工作中 / 等待中 / 验收中 / 下线。
- 当前任务、任务阶段、耗时、最近日志。
- 点击进入任务详情 / 机器人调试。
- SSE 推送，不用 5s 轮询。
- 支持“我的 BOT”过滤。
- 可选的全局动画：工作中流转光效、等待中呼吸、异常红色。

验收标准：打开一个页面能看到“谁在做什么、卡在哪、最近发生了什么”。

### 6.5 供应商 / 成本治理（D4/G3/F8）

当前平台只同步执行器的 provider 缓存，没有真正的供应商管理。

建议：

- 供应商注册：名称、Base URL、API Key（加密）、可用模型、价格。
- 模型目录：上下文长度、能力标签、思考等级。
- 路由：按机器人/团队/任务选择供应商，支持降级。
- 配额与限流。
- 调用计量：session/task/bot 维度记录 token、时长、成本。
- 成本看板：单任务成本、单机器人成本、团队成本。

验收标准：每个任务可回答“用了哪个供应商、多少 token、多少钱”。

### 6.6 指标与 RSI（F4/F5/F6）

先做“北极星 + 五个支撑指标”：

- 北极星：AI 完成任务占比（按数量 + 按交付价值）。
- 交付周期：需求到验收。
- 一次验收通过率。
- 人工介入率。
- 单任务 token 成本。
- 机器人利用率。

数据来源：任务/事件/对话/运行/提测/缺陷/usage。

RSI 闭环：

```text
任务执行 → 事件/对话/文档/复盘留存
→ 提炼经验/失败模式 → 更新知识库/技能/规范/Prompt
→ 回归评测 → 灰度发布 → 监控指标
```

验收标准：复盘能被检索到；机器人配置有版本；更新前后有指标对比。

## 七、关键决策

### 7.1 开发 Agent：OpenCode、自己写，还是 PI？

**结论：继续用 OpenCode 作为执行内核，平台自研编排层；不要回到 PI，也不建议自研通用 Agent Runtime。**

- OpenCode 已具备会话、工具调用、MCP、模型供应商、SSE、提问、权限、中断。
- 平台的差异化在任务状态机、工单/工作流、身份/验收、知识/数据。
- PI 已移除，历史数据迁移为 OpenCode，不要再引入第二套运行时。

边界：

- OpenCode 负责“单 Agent 一轮执行”。
- 平台负责“多 Agent 编排、派单、验收、成本、审计”。

风险：

- OpenCode 版本升级、事件协议变化。建议用 adapter + 契约测试隔离。

### 7.2 Redis 怎么存“思考中”的数据？

**结论：Redis 不是必须；先用 PostgreSQL 分段存储，Redis 只做实时缓冲/扇出。**

建议模型：

- `agent_messages`：一轮对话的消息。
- `agent_thinking_segments`：`sessionId`、`messageId`、`segmentIndex`、`type`（reasoning/tool/text）、`content`、`tokens`、`startedAt`、`endedAt`。
- 前端 SSE 实时流。
- Redis Stream `agent:live:{sessionId}`，TTL 1 小时，只做实时扇出。
- 消费端把 segment 落 PostgreSQL。
- 不逐 token 落库；按段存，保留顺序与轮次关系。

“思考中的数据是否有多次交互”：有。按 `turn → message → segment` 三层存，既能回放，也能按轮次分析。

### 7.3 任务定义和机器人定义的区别

一句话：

> **任务定义是“岗位说明书”，机器人定义是“员工档案”。**

| 维度 | 任务定义（TaskTemplate） | 机器人定义（Worker） |
|---|---|---|
| 回答 | 做什么、输入什么、交付什么 | 谁来做、具备什么能力 |
| 内容 | 类型、描述、默认处理机器人 | AGENTS.md、技能、规范、执行器、模型、负责人、工位 |
| 复用 | 一类任务复用 | 一个机器人可接多类任务 |
| 关系 | 任务定义选机器人池 | 机器人携带上下文与能力 |
| 当前代码 | `task_templates`：name/type/description/agentIds | `workers`：prompt/skills/standards/executor/model/owner |

不要合并两者。合并会导致“任务知识”和“机器人能力”耦合，无法复用。

### 7.4 角色要不要分得更细

**建议：不要先硬编码“前端/后端/测试/运维”角色，先用“能力标签 + 上下文包”。**

- 能力标签：`frontend`、`backend`、`data`、`qa`、`release`。
- 上下文包：服务、仓库、技术栈、规范、知识范围。
- 任务定义声明所需能力。
- 平台按能力匹配机器人。

这样：

- 一个机器人可以同时具备 `backend + data`。
- 一个任务可以要求 `backend + release`。
- 新增服务时只加 context pack，不加新角色。

### 7.5 飞书三种方案怎么选

| 方案 | 适用 | 风险 | 建议 |
|---|---|---|---|
| VPN + 内部站 | 内部员工 | 依赖 VPN，移动端体验一般 | 当前推荐 |
| 飞书内部应用（H5） | 员工日常任务 | 需要应用审核、安全评估 | 第二阶段重点 |
| 开放 + 强登录 | 外部/外包 | 攻击面最大 | 仅对外部人员，配 SSO/MFA/设备信任/审计 |

当前已有飞书 OAuth + Bot 长连接，不需要公网回调地址。下一步重点是把任务操作做成飞书卡片：

- 接单 / 拒绝
- 交付 / 申请验收
- 验收通过 / 返工
- 审批通过 / 驳回
- 复杂操作深链回平台

### 7.6 人作为执行器怎么落地

当前“真人机器人 + 工作台”方向是对的。需要补三件事：

1. **执行队列**：工作台左侧按“进行中 / 等待中 / 已完成”分组，增加领取/排队规则。
2. **飞书卡片操作**：接单、交付、验收、审批都能在飞书完成。
3. **任务交付页**：任务详情 + HANDOFF + 文档 + 日志；交付完成后自动归档。

“一个任务一个群/线程”已经解决上下文区分问题；任务编号 + 群绑定即可，不需要每个任务单独开页面。

### 7.7 BOT 并行与工作目录

- 单 AI 机器人串行是正确的，继续保留。
- 子任务可以并行，但必须由不同机器人执行；同一机器人仍串行。
- 工作目录建议：
  - 每任务一个子目录，或
  - git worktree + 快照。
  - 任务结束清理/归档，产物写入任务文档。
- 不要让多个任务共享同一个工作目录，否则上下文、依赖、端口、临时文件都会互相污染。

### 7.8 机器人生产机器人

建议做成一个“元机器人”流程：

```text
选择历史范围（任务/聊天/文档/复盘）
→ 分析高频工作与失败模式
→ 生成机器人草案：角色、技能、规范、任务定义、模型、工具
→ 生成 AGENTS.md + 评测用例
→ 人工审核
→ 初始化机器人
→ 灰度运行 + 指标评估
```

当前只有“优化 AGENTS.md”按钮，离“生产机器人”还差分析、评测、版本化三步。

## 十、风险与治理

| 风险 | 说明 | 应对 |
|---|---|---|
| 质量风险 | Agent 产出不确定，可能误导验收 | 产物契约、自动校验、人工验收、回归评测 |
| 安全风险 | 密钥、代码、数据被 Agent 读取或外泄 | 凭证网关、最小权限、审计、脱敏 |
| 责任风险 | 机器人出错后责任不清 | 负责人制度、操作审计、任务全链路留存 |
| 依赖风险 | 供应商/执行器故障导致任务中断 | 多供应商路由、降级、重试、超时 |
| 成本风险 | token 消耗不可控 | 配额、预算、成本看板、模型分级 |
| 上下文污染 | 多任务共享工作目录 | 任务隔离、快照、清理 |
| 组织抵触 | 人担心被替代 | 价值评价转向“设计/培训/验收机器人” |

## 十一、组织落地建议

按“高信息密度团队先行”的顺序推进：

1. **第一阶段：技术团队**（后端、前端、数据、测试、运维）
   - 建能力模型、上下文包、开发流、测试流、发布流。
   - 用真实项目验证 AI 交付闭环。
2. **第二阶段：产品与交付团队**
   - 需求分析、方案文档、测试方案、交付验收。
   - 文档机器人与实时预览。
3. **第三阶段：职能与业务团队**
   - 风控、数据、业务支持、市场、行政、财务、人力、法务、运营。
   - 每个团队把自己的专业能力具象为机器人。

人才画像：

- **技能型人才**：能生产专家机器人，覆盖技术、产品、市场、行政、财务、法务等。
- **业务型人才**：能达成业务目标，能带队、能打硬仗、能拿结果。
- 两者可以重合；优先找学习能力强、善用 AI、有专业背景与经验的人。
